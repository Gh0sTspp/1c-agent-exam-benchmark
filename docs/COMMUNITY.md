# Как выполнить замер и отправить результат

Заранее нужны только **Python 3.11+**, **Git** и установленная **платформа 1С с лицензией**.
Всё остальное — GitHub CLI, вход в GitHub, Node.js, Codex или Claude Code, вход в агента,
настройка 1С, проверка грейдера, харнесы — стенд проверит сам и предложит сделать кнопками.
Используйте выделенный компьютер или VM с демобазами.

## 1. Склонируйте и откройте сайт

```sh
git clone https://github.com/zeegin/1c-agent-exam-benchmark.git
cd 1c-agent-exam-benchmark
```

Windows: дважды щёлкните `start-demo.cmd`. macOS/Linux: `./start-demo.sh`.
Виртуальное окружение и `pip install` не нужны: у стенда нет внешних Python-зависимостей.
Откроется `http://127.0.0.1:8879/` — страница «Замер».

Каркас входит в стенд (`starters/carcass-8.3.25.1445/`), скачивать его не нужно.
Это каркас версии 8.3.25.1445;
для описанного замера он загружается платформой 8.3.27.2342.

## 2. Пройдите проверку готовности на странице «Замер»

Стенд сам проверяет компьютер и показывает по шагам, что готово и что сделать:

1. **Аккаунт GitHub.** Если нет Git или GitHub CLI — кнопка «Установить» (winget на Windows,
   Homebrew на macOS; на Linux показывается команда). Затем «Войти в GitHub»: стенд покажет
   ссылку и одноразовый код, вход подтверждается в браузере. Имя и login берутся из аккаунта.
2. **Платформа 1С** ищется в стандартных папках установки, версия берётся из пути; если найдено
   несколько, выберите в списке. Платформу и лицензию нужно установить самостоятельно
   (releases.1c.ru) — скачать их автоматически нельзя.
3. **Защита от опасных действий 1С.** Кнопка «Отключить защиту» дописывает
   `DisableUnsafeActionProtection=.*` в пользовательский `conf.cfg` (с резервной копией),
   иначе 1С остановится с вопросом посреди экзамена. Действует для всех баз этой учётной
   записи; «Вернуть защиту» убирает строку.
4. **Агент** — Codex или Claude Code. Для Codex: если не установлен — «Установить Node.js»
   и «Установить Codex CLI», затем «Войти в Codex» (ссылка и код, нужна подписка ChatGPT).
   Для Claude Code: официальный установщик (команда показывается с кнопкой «Скопировать»),
   затем `claude setup-token` в терминале и вставка токена на странице. Токен хранится только
   в `.local/`. На Windows Claude Code использует Git Bash из Git for Windows.
5. **Изоляция агента** выбирается по ОС. На Windows подтвердите, что это отдельная тестовая
   машина или VM; на Linux нужен bubblewrap.
6. **Каркасная база** входит в стенд, хеш сверяется автоматически.
7. **Проверка грейдера** — кнопка «Проверить грейдер», несколько минут, модель не вызывается.
   1С разворачивает каркас, загружает правильное решение и решение с известной ошибкой и
   проверяет их на трёх сценариях: правильное должно пройти, ошибка — найтись. Делается один
   раз для платформы и версии грейдера. Если не прошла — проверьте, что 1С запускается
   вручную и лицензия активирована, и повторите.
8. **Харнесы** — необязательно; у каждого кнопка «Подготовить».

Когда обязательные шаги отмечены ✓, выберите модель, окружение и лимит и нажмите «Начать экзамен».
Список моделей для каждого агента — в `profiles/agents.json`; новую модель добавляют туда.

Локальные настройки сохраняются в `.local/` и не попадают в Git. Участник
использует собственную подписку агента и собственную лицензию 1С.

## 3. Выберите окружение

Для первого замера достаточно «Без харнеса». Остальные харнесы поставляются описаниями
в `harnesses/<id>.json`: в шаге «Харнесы» у каждого есть кнопка «Подготовить».
Стенд скачивает закреплённые файлы, сверяет SHA-256, устанавливает пакет и проверяет
его реальным вызовом на каркасе. После успешной проверки харнес появляется в выборе
окружения для экзамена. Для skills Широкова нужен установленный Node.js.

Пакеты есть для Windows x64, macOS на Apple silicon (arm64) и Linux x64 — официальные
релизы авторов, у каждого файла закреплён SHA-256. Если для вашей ОС пакета нет, харнес
показан недоступным: другой пакет вместо него не подставляется. Свой харнес добавляется
новым описанием, формат — [docs/harnesses.md](harnesses.md).

Для автоматического открытия EPF в выделенном Windows-контуре настройка 1С
`DisableUnsafeActionProtection=.*` в `%LOCALAPPDATA%\1C\1cv8\conf\conf.cfg`
отключает защиту от небезопасных действий для всех баз данной учётной записи.
Применяйте её осознанно на демомашине; сайт не меняет её автоматически.
Без этой настройки 1С может запросить ручное разрешение. Сведения о таком режиме
сохраняются вместе с результатом.

## 4. Дождитесь решения и оценки

Таймер относится к решению: подготовка и независимая оценка выполняются отдельно.
Раннее завершение агента сразу запускает оценку. Закрытие вкладки не останавливает работу.
Исходники фиксируются до приёмки. Сайт показывает ошибки и границы покрытия:
`≤ 0.5` — верхняя граница балла, а не точный балл `0.5`.

Если сдача отклонена из-за неподдерживаемых индексных привязок субконто,
её исходный статус сохраняется. Для дополнительной оценки существует
`python -m tools.supplemental_acceptance ID_ПРОГОНА`: инструмент выводит виды
субконто из метаданных объявленного товарного счёта и проверяет типы всех ролей
неизменённым адаптером. Это отдельная оценка с доказательством преобразования,
а не исправление исходной сдачи. В публичный пакет включаются обе привязки
и доказательство; такие оценки отделены от оценок оригинальной привязки.

## 5. Подготовьте пакет и отправьте PR

На странице «Мои результаты» можно удалить ненужный завершённый или остановленный
замер кнопкой «Удалить» с подтверждением. Запись исчезнет из личного списка;
исходные материалы запуска сохранятся для повторных оценок. Это не освобождает место
на диске. Результаты с уже отправленным PR удалить нельзя, даже если PR закрыт.
Во время прогона, подготовки пакета или отправки PR удаление недоступно.

1. После оценки нажмите «Отправить в рейтинг» на странице «Замер» или «Мои результаты».
   Стенд загрузит зафиксированный XML в свежую базу и выгрузит `solution.dt`.
2. Раскройте «Что уйдёт в PR» или скачайте пакет и проверьте имя, login, параметры,
   исходники и оценку.
3. Нажмите «Отправить PR». GitHub CLI создаст форк, отдельную ветку
   и PR в `zeegin/1c-agent-exam-benchmark`. Текущая рабочая папка не коммитится.
5. Откройте ссылку PR. После ревью и слияния результат появится на GitHub Pages.

В PR сохраняются:

- полный `src/` с XML, BSL и ресурсами, `binding.json`, трактовки условия, если они сданы;
- `solution.dt`, построенная **из тех же зафиксированных исходников**, и CF, если её сдал агент;
- версия Codex, модель, reasoning, харнес и его хеш, лимит и фактическое время;
- CPU, число логических процессоров, RAM, ОС, архитектура, Python, версия 1С;
- автор, время снимка среды, режим сети и изоляции, ревизия Git и хеши реализации;
- оценка, формальная расшифровка, отпечаток грейдера, SHA-256 файлов.

DT воспроизводит конфигурацию решения, **не рабочие демоданные агента**. XML остаётся
первоисточником для будущего пересчёта. Изменение оценки не должно переписывать
оригинальную сдачу: публикуйте новую ревизию оценки со ссылкой на её manifest.
Исходные логи, домашний каталог клиента, `auth.json`, ключи, лицензии и база рабочего
процесса в пакет не копируются. Авторские XML/BSL сохраняются целиком: проверьте их
перед публикацией так же, как любой свой исходный код.

Файл больше 95 MiB блокирует отправку с объяснением: для такого замера сначала
нужно согласовать долговременное хранилище крупных артефактов; пропускать DT нельзя.

Резервный вариант из CLI:

```sh
python -m tools.community_results prepare ID_ЗАДАНИЯ
python -m tools.community_results pr ID_ЗАДАНИЯ
```

Подготовленные файлы находятся в `.local/community/prepared/ID_ЗАДАНИЯ/`.
Для ручного PR скопируйте эту папку в `community/results/ID_ЗАДАНИЯ/` вашего форка.
DT игнорируется глобальным `.gitignore`, поэтому добавьте именно пакет:
`git add -f community/results/ID_ЗАДАНИЯ`. Не добавляйте `.local/`.

## Независимая перепроверка

Проверка целостности всех пакетов: `python -m tools.community_results validate all`.
Она не запускает код решения. На своей демомашине восстановите `solution.dt`
или загрузите `src/` в исходный каркас, используя версию 1С из `run.json` и
`measurement.json`. Для новой формальной оценки используйте:

```sh
python -m tools.recheck_community ID_РЕЗУЛЬТАТА --output .local/rechecks/ID_НОВОЙ_ОЦЕНКИ
```

Команда использует **вашу** настроенную платформу и проверенный грейдер, сверяет
хеши пакета, повторяет загрузку и сценарии. Исходная оценка остаётся неизменной.

## GitHub Pages для владельца

После публикации репозитория включите `Settings → Pages → Source → GitHub Actions`.
Workflow `.github/workflows/pages.yml` проверяет пакеты, собирает только статический
каталог и публикует его. Ожидаемый URL:
`https://zeegin.github.io/1c-agent-exam-benchmark/`.
Публичный сайт — только рейтинг; замер выполняется из клона репозитория.
Пересчёты группируются по исходному `run_id`: одна строка рейтинга показывает
последнюю по времени оценку, предыдущие доступны через «Открыть прогон» →
«История и данные» → «Предыдущие оценки». В `community.json` они лежат в `previous_evaluations`.
Каждая оценка сохраняет отдельный архив с исходными DT/XML и отчётами; пересчёт
не удаляет прежние пакеты и не считается ещё одним прогоном агента.

В рейтинге откройте прогон и разверните «Показать код или метаданные» в карточке
штрафа. Если проверка сохранила координаты, сайт покажет метод BSL с выделенной
строкой или дерево свойства метаданных. Контекст берётся из сохранённого решения
именно этой оценки; если точное место не установлено, карточка сообщает об этом.

Централизованную перепроверку владелец запускает из настроенного стенда с 1С
и входом в GitHub CLI под учётной записью владельца репозитория:

```sh
python -X utf8 -m tools.recheck_community SUBMISSION_ID --output .local/rechecks/NEW_ID --owner-server "Owner Windows stand" --publish-owner
```

`--output` должен указывать на новую папку. Параметр `--owner-server` задаёт публичное
название сервера. После завершения создаётся новая квитанция в `community/rechecks/`;
её нужно включить в коммит, чтобы она попала на Pages. Исходный пакет не меняется.
Без `--publish-owner` результат остаётся локальным. Технический сбой до получения
оценки не публикуется как завершённая перепроверка.
Если допуск к оцениванию пройден, но отдельные наблюдения 1С завершились ошибкой,
владелец может сохранить частичную проверку с помощью дополнительного ключа
`--publish-incomplete` вместе с `--publish-owner`. Она явно отмечается как
неполная и не получает места в рейтинге. Другие ошибки этот ключ не разрешает.

На сайте новая оценка получает отметку «Проверено владельцем репозитория».
В разделе «История и данные» указаны проверяющий, дата, профиль грейдера, коммит, наличие локальных
изменений, SHA-256 полного набора входов грейдера, название сервера, CPU/RAM/ОС
и точная версия платформы перепроверки. Параметры исходного запуска агента и его автор
сохраняются отдельно. Архив содержит исходный пакет в `original/` и новую квитанцию
`owner-recheck.json`. Отметка не означает успешного решения или полного покрытия.

При проверке запроса с табличным параметром сообщение платформы об отсутствующем
поле само по себе не доказывает ошибку: структура параметра может быть неизвестна
при статическом разборе. Такая проверка отмечается как неполная; ошибка, подтверждённая
выполнением, по-прежнему учитывается. Калибровка проверяет на платформе оба случая.

Для исправления этой проверки владелец может пересчитать сохранённые наблюдения
без повторного запуска решения. Команда сверяет исходники, прежнюю версию грейдера,
воспроизводимость прежней оценки и границы изменения; прежняя квитанция сохраняется:

```sh
python -X utf8 -m tools.reassess_community SUBMISSION_ID --prior .local/rechecks/OLD/evaluation.json --revision OLD_GRADER_COMMIT --output .local/rechecks/NEW --publish
```

Квитанция указывает, что использованы сохранённые наблюдения 1С. Для неполной
перепроверки требуется явный `--allow-incomplete`; она показывается как неполная
и не получает место в рейтинге.

Сайт не требует 1С, модели и ключей на сервере GitHub. Сборка не запускает присланные решения.

Рейтинг разделён по условиям, включает автора и параметры машины. Заявленные участником
оценки не выдаются за независимо подтверждённые. Неточные верхние границы показываются
без места в рейтинге. PR-проверка проверяет структуру и хеши, а не решает экзамен заново.
Пакет, оценённый другой версией грейдера (его `grading-implementation.json` не совпадает с текущим
кодом), тоже принимается: оценка показывается с пометкой «требуется пересчёт» и без места, пока
решение не переоценено текущим грейдером. Так же помечаются оценки адаптером привязок, которого
нет в репозитории, и пакеты, где исходная сдача не прошла приёмку, а доказательства адаптера нет.
Для отображения применяются только отдельно проверенные исключения совместимости:
например, изменение подсчёта токенов Claude в коммите `4a0ad81` не меняло оценивание.
Исключение привязано к конкретным хешам старого и нового файла; иные изменения
по-прежнему требуют пересчёта. Исторические отпечатки и квитанции не переписываются,
а требования к актуальности калибровки сохраняются.

Для владельца перед открытием репозитория: проверьте Git-историю и права на публикацию
сторонних материалов. Смена видимости и включение Pages — отдельные действия владельца;
новые локальные замеры автоматически в Git не отправляются.

Официальные справки: [Pages Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages),
[GitHub CLI PR](https://cli.github.com/manual/gh_pr_create).
